# 2026-10-09 — launcher worktree reuse and the recreate trap

**Asked.** Verify relaunch idempotence of worktrees in `sighting/tower-fleet.mjs`.
**Sources.** `sighting/tower-fleet.mjs` (:610, :737-754, :761-766, :797-819, :907-928, :935-946, :1006-1149, :1220-1224); `omp worktree` probes in scratch `/tmp/wtp-reuse*`.
**Observed.**
- **Reuse is `existsSync`-only.** The entire reuse decision is `if (existsSync(row.worktree)) { record.worktreeReused = true; }` (:798-799); `assertSafeWriteTarget` (:257-285) checks only dangling/symlink/containment/substrate, never that the path is a git worktree or on the expected branch. Proved: a tree with HEAD detached, an empty dir, and a plain file all satisfy `existsSync` (exit 0) yet `git -C <dir> rev-parse --abbrev-ref HEAD` → `fatal: not a git repository` exit 128; the same empty dir was still addable (`omp worktree add -b tower/g/empty <empty-dir> main` → exit 0). omp itself already refuses to clobber the path (`fatal: '<path>' already exists`, exit 1), so the gate prevents `WORKTREE_ADD_FAILED` rather than clobbering. The launcher never calls `omp worktree list`; `record.branch` (:742) is the *intended* branch (:610), not an observation.
- **Reuse is silent** (:798-800 has no warn call); the only worktree-related warn (:803) is `mission <id> reuses a wall row but its worktree <path> is missing`, and it fires only when a wall row was adopted and **before** the add (intent, not outcome — the same line prints on both the `worktreeRecreated` and `worktreeMissing` paths). `worktreeReused`/`worktreeRecreated`/`worktreeMissing` are mutually exclusive by construction; a fresh successful create leaves **no** create signal at all, and `worktreeMissing` is absent from the record literal (assigned only at :814) so consumers cannot distinguish false from unchecked.
- **The recreate trap (high).** `close` prints `git -C <repo> worktree remove <path>` (:1220-1224), which removes the **tree** but leaves the branch `tower/<fleet>/<id>` behind. A later relaunch only recreates the tree when the retained branch still equals base: reproduction `wtp6` — CASE1 (branch == base) `add` exits 0, tree yes; CASE2 (branch carries its own commits) `omp add` refuses the ref write (`git branch: Reference "refs/heads/tower/f/adv" was not supposed to exist when writing it with value Object(Sha1(2d02198…)), but actual content was Object(Sha1(ac708c4…))`), exit 1, no tree, branch still `ac708c4` → the launcher records `WORKTREE_ADD_FAILED` (+ `worktreeMissing` only if a row was adopted). An `rm -rf` of the tree instead yields `git worktree add: refs/heads/tower/g/empty is already checked out`, exit 1, path later prunable. So `worktreeRecreated` is reachable **only** for a lane whose branch never moved off base.
- Second SKILL drift: `SKILL.md:152-153` claims a failed worktree `add` aborts the run outright; the code records a per-mission failure, still writes `fleet.json` (:905-928), and ends `LAUNCH_PARTIAL` exit 2 (:945-946).
**Changed.** Seed entry.
**Unknown.** Whether a wall-adopted row's missing tree is always accompanied by a stale branch (depends on how a prior close/rm left the branch).
