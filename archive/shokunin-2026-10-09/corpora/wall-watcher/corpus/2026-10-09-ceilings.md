- **Geometry vs ceiling, corrected.** This is *not* "layouts = display, windowPaneCeiling = enforcement".
  - `layouts` rows×columns is the **enforced** default-window mission cap (15 at 16:9; 18 at 21:9) — and it
    is also the rendered grid.
  - `windowPaneCeiling` is the **enforced** fleet-window mission cap **and the input to that window's grid**
    (`fleetLayoutContract`: rows 3, `maxColumns = ceil(cap/3)` = 6 → 18 layout cells for a cap of 16), and it
    is boot-read (and validated) on every wall invocation, so it is never dead config.
  - The enforced quantity is a **mission count**, never a tmux pane count; the overview strip is excluded
    from the counted set (it consumes grid height, not a cell). Live proof: window 1 holds 2 panes for 0–1
    missions, window 2 holds 8 mission panes.
- Ordering: `assertL1Capacity` runs **before** `assertCapacity`, and the launcher's L1 gate before its pane
  gate — so under the live 16/16 band the pane arms (`CAP_EXCEEDED` for a fleet window,
  `PANE_CEILING_EXCEEDED`) are **shadowed** by `L1_CEILING_EXCEEDED` and are reachable only when
  `windowPaneCeiling < maxConcurrentL1` (test-pinned with `pinnedCeilingFixture(16, {maxConcurrentL1:32})`).
  Even the 21:9 cap 18 is unreachable — the 17th launch is `L1_CEILING_EXCEEDED`.
- Gate populations differ: the launcher compares the **spec's own** mission count; the wall's
  `assertL1Capacity` compares the **live global** count across every fleet + the default wall. So a fleet
  can be admitted up front and still come up partially — a per-mission wall refusal lands as the launcher's
  `LAUNCH_FAILED` (wall code only inside the detail string) and the run exits `LAUNCH_PARTIAL`.
