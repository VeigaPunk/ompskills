# substrate-clobber-2026-10-09 — the band authority was overwritten once, and how

Asked: (incident record, written by the L1 while preparing round 2) why `ufo-fsd-alpha/config/ufo.json` read `{"drills":{}}`.

Observed:
- 2026-10-09 16:27:12 −03: substrate `config/ufo.json` became 13 bytes, `{"drills":{}}`, sha `431644a4…`. Every live reader (wave validator, launcher, wall, dispatcher) would have refused or misread policy.
- Writer: fleet `shokunin3`, mission **drill-keeper**, lane `VGatesDrillsHistory`, at 19:27:12Z. The command was `cd /home/vgpnk/Projects/ufo-fsd-alpha && … ; cd /tmp/gk/pre_cfg && (…); printf '%s' '{"drills":{"enabled":null}}' > config/ufo.json; …`.
  In this bash tool `cd` can fail (`error: command not found: __fnmcd`), which leaves the cwd in the substrate, so a **relative-path redirect** lands on the band authority. `/tmp/gk/pre_cfg/config/ufo.json` was a real file, not a symlink, so this was not a symlink write.
- Restore: drill-keeper's L1 killed the lane (`proc://VGatesDrillsHistory/kill`). At 19:30:50Z it wrote the bytes from a sha-verified scratch copy (`test ! -L` on both paths, sha prefix `0e416f0abc559e9a` checked) and broadcast a stop-rule to `agent://all`.
  The ceiling-keeper L1 independently rebuilt the known-good bytes off-substrate (HEAD + the three working-tree hunks → sha `0e416f0a…`) at `/tmp/ck-goodcfg/config/ufo.json`, but did not need to write them. It confirmed the restored file is a regular file with sha `0e416f0a…`.
- ceiling-keeper's own lanes: a transcript scan found **no** write/edit/redirect to the substrate. One r1 lane (WallGeometryCap) issued an `edit` mis-addressed to `scripts/ufo-sighting.mjs`; the edit tool refused it (anchor never displayed) and the file is unmodified.

Rules this teaches (for any numeric probe):
- Never `cd` and then write relatively. Write only to absolute paths under a fresh `mktemp -d`. Prefer the tool's `cwd` parameter over `cd`.
- Re-hash `config/ufo.json` before trusting any probe, and before and after a wave.
- A restored file can carry the same sha with a new mtime. `stat` mtime alone is not proof of tampering, and sha alone does not show the event happened.
